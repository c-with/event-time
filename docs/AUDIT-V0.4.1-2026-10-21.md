## 1. 审计结论

**结论：当前版本不宜继续扩展业务功能，应先完成 P0/P1 稳定性整改。** 已确认通用弹窗错误关闭机制及任务编辑字段契约冲突；还有改期确认弹窗生命周期、设备时区、分事务写入等可由静态代码明确推导的风险。数据库健康检查和早前 4/4 单元测试不能覆盖这些缺陷。

### P0-01 — 通用编辑弹窗点击即关闭（确定性代码缺陷）

- **证据：** `static/app.js:L442-L460` 的 `.modal-backdrop` 携带 `data-action="close-modal"`；`L632-L638` 的全局处理调用 `e.target.closest('[data-action]')`；`L683` 把该处理器绑定到 `modalRoot`。
- **根因：** 点击表单内普通输入、下拉、日期时间控件时，事件沿 DOM 冒泡，`closest` 会返回带关闭动作的祖先遮罩；内层另一个遮罩点击处理器虽检查 `e.target`，仍挡不住全局代理先关闭。
- **影响：** 项目、场次、任务、资源、资料上传等使用 `openModal` 的表单均有误关闭风险，正在输入的草稿丢失。
- **整改：** 遮罩本身不参与向上 `closest('[data-action]')` 关闭分发；独立监听遮罩并严格限定 `e.target === backdrop`，关闭按钮用单独动作。弹窗内容区点击、下拉展开、日期选择、文件选择均不关闭。
- **门禁：** 在桌面 Chrome、Android Chrome、iOS Safari，逐项点击/更改输入框、`select`、`datetime-local`、多选关联、文件控件，弹窗持续存在；点击遮罩/关闭按钮才退出。

### P0-02 — 编辑任务必带的关联字段被后端白名单拒绝（确定性代码缺陷）

- **证据：** `static/app.js:L553-L562` 表单定义并提交 `dependency_ids`、`requirement_ids`；`app.py:L89-L101` 普通 FIELD_ALLOWLIST 无这两个关联字段；`app.py:L518-L524` 拒绝未知字段；`app.py:L993-L1018` 却在调用该校验后才处理关联字段。
- **影响：** 正常任务编辑请求可能直接 400；工作包 `session_ids` 与需求 `task_ids` 的 PATCH 也有同类契约矛盾。
- **整改：** 将关系字段与标量字段分离验证；一次性验证关联对象归属、环依赖和修订版本，再在同一事务提交；为合法/非法组合添加后端接口测试。
- **门禁：** 新建任务，编辑名称、截止日期、依赖及关联需求后 API 200 且数据库回读一致；非法跨项目关联/循环依赖返回 400 并保证所有字段完全未修改。

### P1-03 — 第二级改期确认弹窗被第一级表单自动关闭（强证据）

- **证据：** `static/app.js:L445-L457` 通用提交器固定 `await onSubmit(payload); closeModal()`；`L708-L720` 手工“预览改期”在 `onSubmit` 内再次调用 `confirmModal` 打开第二个弹窗。
- **影响：** 第二级确认可能在事件处理完成后立刻被父级无条件 `closeModal()` 销毁，造成按钮无法确认或界面闪烁。
- **整改：** 按弹窗实例/唯一 token 管理关闭权，提交后仅关闭发起该提交的旧弹窗；升级确认时不关闭新弹窗；提交失败保持原值和表单。
- **门禁：** 手工改期：输入时间→预览影响→确认弹窗持续停留→取消无写入→确认才产生修改与审计。

### P1-04 — 日期时间按浏览器本地时区展示/写回（数据准确性风险）

- **证据：** `static/app.js:L37-L43` 用 `new Date(value)` 及设备本地 `getHours()` 生成 `datetime-local` 输入；`L735-L738` 拖动跨日期时使用设备本地时区；`app.py:L222-L238` 对没有时区信息的输入默认使用 `Asia/Shanghai`。
- **影响：** 设备设置成 UTC+09:00 时，已保存的北京时间 16:00 可能在编辑框显示 17:00，写回后产生一小时偏移；日历拖动同样有风险。
- **整改：** 业务时间统一按 `Asia/Shanghai` 显示和编辑，采用明确的日期/时区转换工具与往返不变测试；不得依赖访问者设备默认时区。
- **门禁：** 用 UTC+08 与 UTC+09 两种浏览器时区查看、编辑、保存同一场次，时间和 UTC 瞬间必须一致。

### P1-05 — 多字段与关联关系未统一成原子事务（确定性结构缺陷）

- **证据：** `app.py:L518-L586` `apply_entity_changes` 在提交标量字段后立即 `db.session.commit()`；`L960-L1018` 中工作包/需求/任务关联字段随后验证并提交，错误时可能已经修改标量字段。
- **影响：** API 返回错误不一定意味着整个请求没写数据；操作人与审计可能看到不一致状态。P0-02 修复后这个问题更容易暴露。
- **整改：** 校验全部字段和关联 → 一次事务写入 → 一次提交；任何失败整体 rollback；审计、修订号、关联记录同事务。
- **门禁：** 发送“合法名称 + 非法关联”请求，收到 400 且名称、关联、revision、审计均未变化。

### P1-06 — 生产入口使用 Flask 开发服务器（部署健壮性）

- **证据：** `app.py:L1479-L1494` 最终调用 `app.run(... threaded=True)`；`Dockerfile` 默认 `python app.py serve`。
- **影响：** 不符合生产 WSGI 部署惯例，长期运行、并发、上传和超时处理缺少相应生产级运行配置。
- **整改：** 容器使用 Gunicorn 等正式 WSGI 服务器并设置适当 worker、timeout、日志和健康检查；验证对单实例和多 worker 的数据库/文件操作无误。

### P1-07 — 自动化覆盖与系统功能不匹配（已确认）

- **证据：** 当前 `tests/test_merge_logic.py` 为 4 个旧合并算法单元测试；新 ORM/API 的任务编辑、时间处理、上传、审批、改期等均无对应测试文件。
- **影响：** 此前 4/4 PASS 不能证明本次 P0/P1 核心操作正常。
- **整改：** 新增 Flask TestClient + 临时 SQLite / PostgreSQL 集成测试、Playwright 浏览器回归，尤其覆盖上述故障；CI 门禁纳入脚本。

### P2-08 — 文件上传内存开销与去重未落地（需要补强）

- **证据：** `app.py:L1295-L1316` 为统计大小先完整读取所有上传文件，再逐个 `file.read()`；`L1204` 为每份文件重新生成 ID，`L1323-L1338` 直接创建记录，无同哈希已有文档复用的分支。
- **影响：** 100–250MB 批量上传可能产生高内存峰值；相同内容重复上传仍创建新的实体与物理文件。
- **整改：** 流式写临时文件 + 分块哈希 + 尺寸上限；事务确认后转正；根据 SHA256 与文件保留语义进行内容去重，允许多业务关联，保留文件版本语义。

### P2-09 — 日历色彩只能区分部分活动，不能保证同日唯一（范围限制）

- **证据：** `static/app.js:L204-L212` 场次 ID 哈希到 12 种颜色；`L273-L286` 每格仅展示前三项。
- **影响：** 同一天超过 12 场或哈希碰撞可能撞色，同项目多个场次可能不同色；虽然已添加“查看全部”弹窗，但不能用颜色代表稳定的项目关系。
- **整改：** 定义“同项目同色、场次用文字/线型区分”还是“每场次独立色”的明确规则；日历显示序号/简称作为第二视觉通道，并测试同日多活动。

### P2-10 — 编辑后离开无草稿保护（用户体验与数据完整性）

- **证据：** `static/app.js:L474` `closeModal` 直接清空 DOM；`L753` 按 Escape 无条件关闭。
- **影响：** 正在编辑的信息可能因误触遮罩、Escape、导航而丢失，且不会提示未保存修改。
- **整改：** 表单 dirty tracking；关闭、切换页面前显示放弃修改提示；只在成功提交后清理。

### P2-11 — 重要字段可由客户端 flag 绕过提案流程（控制一致性）

- **证据：** `app.py:L518-L561` 是否直接修改重要字段取决于请求传入的 `critical_confirmed`；各 PATCH 接口从 `confirm_critical` 映射；`static/app.js:L564-L568` 任务快捷状态变更直接发送 `confirm_critical:true`。
- **影响：** 如果产品要求“重要操作必须经过人工明确确认”，单一请求字段不足以证明发生过确认交互；快捷操作存在跳过确认提示的路径。
- **整改：** 把显式确认步骤的记录/一次性确认语义落在服务端；任务快捷完成应有清晰的确认或按冻结需求重新划分普通/重要变更。

## 2. 建议修复顺序

**Gate R0（阻断性，优先）：** P0-01、P0-02、P1-03、P1-04、P1-05。按功能提交小型修复，完成回归测试；不可只做 CSS 改色或把错误捕捉后吞掉。

**Gate R1（可靠性）：** P1-06、P1-07、P2-08、P2-10、P2-11。将操作失败无部分提交、登录/CSRF、文件与备份恢复纳入回归。

**Gate R2（交互完善）：** P2-09 及日历跨月、多活动、择日窗口、空白日期、旧日期灰显、移动端密度等用户场景。

## 3. 核心验收矩阵

1. 项目编辑：修改名称、负责人、客户、说明，逐个输入框可保持焦点并最终回读。
2. 场次编辑：改时间、状态、场地、备注；修改重要字段进入待确认，确认后才生效。
3. 任务编辑：依赖多选、需求关联、负责人、截止时间；合法提交成功，非法组合全事务回滚。
4. 改期：预览显示旧/新时间、移动节点、固定承诺；二次弹窗不会消失；取消不写入。
5. 日历：10/26 与 10/30 多场并列、窗口候选、连续多日与跨月显示正确；点日期有完整当天信息。
6. 附件：文件选择/上传、失败项、PDF 原件与预览、图片方向与压缩、分享撤销。
7. 时区：浏览器在亚洲上海与东京设置下保存/编辑一致。
8. 安全：未登录 401、缺 CSRF 403、跨项目关系无效 400、字段冲突 409。
9. 数据：失败请求不能部分写入；revision、ChangeRequest 与 AuditLog 一致。
10. 部署：后台健康、Docker 日志、数据库与附件联合备份/恢复，部署期间既有 8600 有可回滚路径。

## 4. 发布纪律

- 本报告只证明源码中可见的机制及风险；**不能宣称已经在真实浏览器复现所有问题**。
- 先在测试副本部署并验收，再切换正式服务。
- 所有修复都需单独 commit、测试记录、精确变更文件列表；不得提交 `.env`、内网资料、数据文件或密钥。
- 生产变更前备份 PostgreSQL 和附件，并验证可恢复；不要在生产直接清空、覆盖或重建数据库。
