# 活动执行工作台 V0.4.1 — 业务需求基线（确认项合并版）

-   **更新日期**：2026-10-20
-   **状态**：需求规格更新；不修改代码、不执行数据库迁移、不部署。
-   **文档性质**：业务需求和验收基线，不代表软件已实现。
-   **版本关系**：本文件整合此前 V0.4 业务逻辑基线和后续确认项；若与旧任务书冲突，以本版为准。

## 1. 本次已确认的决策

1.  **项目是业务上层主线**。项目下可有零到多个活动场次、物料订单、执行工作包、需求项和执行任务；纯物料项目可以没有活动场次。
2.  **ID 只作为系统内部唯一主键**。系统生成、永久稳定、不可人工修改；不作为日常沟通编号，不另设业务展示编号，普通列表默认隐藏。
3.  **主图规则**：项目主图作为默认封面；项目下每个活动场次可单独设置主图。场次未设置时使用项目主图；两者均无图时显示统一占位图。
4.  **项目列表默认排序**：近期执行优先，逾期和重要风险置顶；可切换其他排序方式。
5.  **日历过去时间灰显**：过去的活动/节点降低饱和度，但未完成、逾期或有重要风险时仍须显示醒目的风险标记。
6.  **日历改期**：桌面端支持拖动；拖动后先显示变更预览，点击确认才生效，取消则恢复原位。移动范围按项目/场次关系和时间节点关联规则处理。
7.  **连续多日活动**：同一个场次按真实起止日期显示为连续条带；跨周、跨月保持连续语义。择日窗口不得画成连续举办多日。
8.  **统一执行节点标签**：至少包含布场、彩排、活动、撤场、交付、截止；图标、文字和颜色共同表达，不能只靠颜色。
9.  **资料附件**：场地档案、楼栋/楼层/厅室、设备档案及基础资料库支持图片和 PDF 上传；项目执行中心也可关联或上传活动专属文件。
10. **协作方式**：单一共享账号，不区分角色；每台设备记住上次选择的操作人姓名，重要操作重新确认。
11. **重要变更**：记录修改前后、来源文件/来源信息、提出人、确认人、确认时间和历史恢复；任何同事均可确认。
12. **并发冲突**：字段级冲突检测，只处理冲突字段；不同字段的并发修改可以合并。
13. **期限管理**：系统按已知工期和依赖倒推建议期限，由活动负责人确认；缺少可靠工期时不生成虚假的精确日期。
14. **文件保留**：普通照片压缩、校验成功后只保留压缩版及必要缩略图；重要 PDF 保留原件。处理失败时不能先删除唯一有效副本。
15. **实施边界**：先让核心工作台可靠运行，AI 和对象存储后续接入。新版 Docker 化并复用现有 PostgreSQL；先在独立测试入口验收，不覆盖当前 8600/SQLite 服务。

## 2. 唯一业务主线

**需求登记 → 建立/定位项目 → 确认基本信息与场次 → 分工作包 → 建立需求清单与执行任务 → 确认时间与期限 → 执行验收 → 文件归档 → 历史复用。**

项目名称、客户、日期、场地、负责人和主图都可能变化，但 `project_id` 不变。日历、项目列表、近期执行提醒和全局检索是同一业务数据的不同视图，不得分别维护事实。项目可以暂缺日期、客户、场地或供应商，允许先建立草稿；不得为了让项目出现在日历上而编造日期。疑似重复项目只提示比较，不自动合并。

## 3. 核心业务对象与关系

### 3.1 项目 Project

代表一项整体承接工作，可以是活动执行、多场次宣传活动、纯物料制作、布场支持或设备租赁。项目具有内部唯一 `project_id`、名称、客户、主要负责人、项目阶段、项目主图和关联对象。名称可修改；同名项目允许存在，但新建时提示可能重复并展示客户、日期、场地供人工判断。

### 3.2 活动场次 Session

项目下零到多个实际可排期单元，可有不同日期、地点、厅室、彩排和供应商进场时间。纯物料项目可以没有场次。场次具有内部唯一 `session_id`、所属 `project_id`、起止时间、时间确定状态、场地/空间、场次专属主图（可选）和关联节点。场次主图覆盖项目默认主图；未设置时继承项目主图作为显示默认值，不复制或覆盖项目主图文件。

### 3.3 时间节点 Time Node

可归属于项目、场次或工作包，允许同类型多条，例如多批进场、多次彩排、不同工作包的不同撤场时间。节点类型至少包括布场、进场、彩排、活动、撤场、交付、截止。分别保存计划、确认和实际时间、负责人/责任方、来源、状态，以及"跟随场次移动/固定承诺"的关联规则。原文如"活动 16:00，08:00 到"含义不清时必须保留原文并待确认，不得擅自解释。

### 3.4 执行工作包 Work Package

项目下可独立分派、跟进和验收的一部分工作，如 LED、音响灯光、舞台、印刷。可暂时没有供应商；一个供应商可负责多个工作包；一个工作包可关联多个场次。更换供应商需保留历史分派记录。

### 3.5 需求清单项 Requirement Item

记录真正需要的物件或服务，例如 LED、麦克风、长条桌、背景板、画架、讲台。包括名称、原文、规格、尺寸/单位、数量/单位、用途/位置、来源、确认状态、实际交付数量和验收要求。需求项不等于任务。

### 3.6 执行任务 Task

记录催名单、核尺寸、定稿、打样、制作、运输、布场、调试、验收、撤场和回收等动作。任务有执行人、责任方、计划/截止/实际时间、依赖关系、状态和完成证据。任务可关联一个或多个需求项，也可不关联物料。跨工作包共用的保障事项使用一个任务 ID，由多个工作包引用，避免重复分派。

### 3.7 长期资源库

包括客户与联系人、供应商公司与联系人、场地空间、固定设备、自有资产、标准物料/工作包模板和历史案例。项目引用资源库，但历史项目保留本次实际使用快照；主档更新不能静默改变历史事实。联系人与供应商公司分开建模，无法确认所属公司时可先保留联系人和原始文字，不猜测供应商归属。

## 4. 页面结构

### 4.1 首页：日历台账 + 今日/近期执行

支持月/周/日视图、待排期列表、今日/明日布场、即将彩排、活动、撤场、交付、逾期任务、重要变更待确认。日历是业务数据视图，不是独立数据源。点击任一活动条进入同一项目执行中心，并定位到对应场次。

### 4.2 项目总台账

默认紧凑列表，可切换卡片视图。主要显示项目主图、项目名称、客户、项目阶段、最近/下一场活动时间、场地、主要负责人、下一项关键行动、风险提示和最近更新时间。内部 ID 默认不显示，也不作为团队日常沟通编号。

### 4.3 项目执行中心

集中完成大部分操作，包括：项目总览与待办、场次与时间轴、工作包/供应商、需求清单、执行任务/依赖、文件与版本、变更历史、验收收尾和归档。跳转资源档案后应能返回原项目上下文。

### 4.4 资源总库

跨项目维护客户、供应商、场地、设备和模板。项目中可以直接引用资源。场地档案、设备档案和基础资料库均须支持图片/PDF 上传。

### 4.5 手机端

优先显示近期执行、时间、场地/联系人、任务状态、批量上传现场照片和查看 PDF。复杂批量编辑可优先在桌面端完成，但手机端不能因此无法查看或补充关键现场资料。

## 5. 项目主图规则

-   每个项目最多指定一张当前主图，优先使用正式主 KV/主画面。
-   项目下每个场次可指定独立主图；未设置时继承项目主图。
-   项目和场次均无图时显示统一占位图。
-   主图可从已上传附件中选择，也可直接上传；支持预览和替换。
-   更换主图只改变当前封面引用，不删除旧附件、历史版本或正式交付文件。
-   列表缩略图使用统一比例；详情可查看完整图片。
-   上传失败时保留原主图，不得用空白封面覆盖有效主图。

## 6. 项目列表排序与状态

### 6.1 默认排序：近期执行优先，逾期和重要风险置顶

1.  **最高优先**：已逾期关键任务、时间冲突、可能影响执行的重要变更待确认、关键节点已过但未完成。
2.  **今日执行**：今天的布场、彩排、活动、撤场和交付。
3.  **明日执行**：明日布场、彩排、活动和交付。
4.  **未来 7 天内有关键节点**：按最近节点时间升序。
5.  **其他筹备/待排期/待补资料**：按下一项行动时间；无时间时按最近更新时间。
6.  **收尾中**：优先展示仍有未完成任务或待补归档材料的项目。
7.  **已完成、已取消、已归档**：默认收起或置后；存在未解决风险时仍须在风险视图可见。

同一组内按最近关键节点时间排序，再按最近更新时间排序。可切换按活动日期、最近更新、项目名称、客户、负责人或项目阶段排序。切换排序不改变业务数据，并保留当前筛选条件。系统应能解释项目被置顶的原因。

### 6.2 状态分层

-   **项目阶段**：新登记、筹备执行、现场执行、收尾、已完成、已取消、已归档、搁置。
-   **排期状态**：待排期、日期窗口/择日、暂定、已确认、存在冲突。
-   **工作包状态**：待指派、待确认、准备中、现场执行、待验收、已完成、取消。
-   **需求状态**：待澄清、待确认、已确认、已交付、已验收。
-   **任务状态**：待办、进行中、阻塞、待确认/待验收、已完成、取消。
-   **风险标记**：逾期、时间冲突、资料待补、供应商未确认、重要变更待确认等。

显示名称、颜色、图标可以配置；底层语义码和状态转换规则必须稳定。不能把"已完成"的底层语义随意改成"筹备中"。风险优先由系统根据任务与时间计算，不只依靠手工选择。

## 7. 日历视觉与交互

### 7.1 过去时间灰显

已过去且完成的活动/节点降低饱和度；已取消项目浅灰并明确标注取消。过去但未完成或逾期的项目仍保留醒目风险角标。今天高亮，今日执行节点突出显示，未来项目正常显示。过去与否按活动/节点的结束时间判断，不按创建时间或更新时间判断。

### 7.2 连续多日活动

-   一个场次按真实起止日期绘制连续条带，不每天创建重复业务记录。
-   同周连续显示；跨周/月时在边界截断但保持同色并显示延续语义。
-   点击任一段进入同一个场次/项目执行中心。
-   标题尽量只在起始段显示；日历拥挤时可折叠为"另有 N 项"，但仍可访问。
-   择日窗口（例如某日期范围内任选一天）用虚线/范围提示，不画成连续实心活动条。
-   不同场次即使名称相似也不强行合并。

### 7.3 拖动改期与确认

1.  桌面端拖动活动条；手机端提供"调整日期"，两者使用同一确认流程。
2.  拖动后先进入预览，不立即写入正式数据。预览显示原/新日期、受影响节点、关联任务、期限建议、供应商承诺和潜在冲突。
3.  取消后恢复原位；确认后原子提交，记录审计并重新计算风险。
4.  默认只移动当前场次及明确标记为"跟随场次"的相对节点。调整整个项目排期必须显式选择，并列出受影响场次。
5.  相对布场/彩排/撤场节点按关联规则移动，保留时分和持续时长。
6.  固定截止日期、已确认供应商交期和外部预约不静默覆盖；预览中提示复核，由用户决定是否调整。
7.  系统期限建议可重新计算，但不能覆盖供应商承诺日期。
8.  同一字段被另一台设备同时修改时，显示冲突双方的值，禁止最后写入者静默覆盖。
9.  保存失败时保持原数据并提示失败，不能出现日历已移动但后台未保存的假成功。

## 8. 固定节点标签与提醒

  标签   建议图标    用途
  ------ ----------- -------------------------------------------
  布场   工具/锤子   舞台、背景板、LED、音响灯光安装与现场布置
  彩排   麦克风      流程演练、设备调试、人员走位
  活动   日历/旗帜   正式活动举办时间
  撤场   货车        拆除、清运、回收、离场
  交付   包裹/勾选   制作交付、运输交接、现场验收
  截止   时钟/警告   定稿、名单、制作等关键期限

标签同时显示图标和文字，颜色只作辅助。允许增加自定义标签，但不能用它们替代系统关键节点。

有确定活动日期时，系统可建议"活动前一天布场"，但未经确认只能显示为建议/待确认。用户可改为提前多日、当天或分批进场；不同供应商可有不同进场时间。场次改期时，相对布场节点跟随移动，固定预约进入复核。首页显示今日/明日布场、即将彩排、活动、撤场、交付、逾期任务和重要变更待确认。时间未定的关键布场事项仍进入待确认区。

## 9. 场地档案、基础资料库与附件

### 9.1 上传范围

场地、楼栋、楼层、厅室、室外区域、固定设备、自有资产、客户、供应商、标准物料/工作包模板、项目、场次、工作包、需求项和任务都可关联图片/PDF。场地档案和基础资料库必须具备图片与 PDF 上传能力。

### 9.2 统一附件能力

-   单文件和批量上传，支持混合图片/PDF；显示进度、失败项和单项重试。
-   图片缩略图/预览，PDF 在线预览和下载。
-   文件类型、大小、上传人、上传时间、来源、哈希、版本和关联对象可查。
-   同一物理文件可以关联多个业务对象，但关联记录独立；同名文件可以并存，不能仅按文件名覆盖。
-   文件可关联项目、场次、场地空间、设备、供应商、工作包、需求项和任务。
-   分享链接针对明确版本，支持有效期和撤销；已下载到外部设备的副本无法远程收回。

### 9.3 文件保留规则

-   普通照片：临时接收 → 方向校正 → 压缩 → 校验 → 成功登记 → 清理原始上传副本；只保留有效压缩版和必要缩略图。
-   透明 PNG、图纸或细线图片不能盲目转成不透明 JPEG。
-   重要 PDF 保留原件；优化版仅作为预览副本。
-   处理失败时不得先删除唯一有效副本。
-   正式文件被项目引用后不得静默替换内容；删除/替换应确认并留痕。

### 9.4 场地资料结构

场地采用层级：场地 → 楼栋/区域 → 楼层 → 厅室/具体位置；室外区域可无楼层。设备资料应区分 LED 物理尺寸、分辨率、像素间距；货梯门尺寸与轿厢内部尺寸；装卸点、运输路线、车辆限高、供电、音响灯光情况。关键参数记录来源、最近核验日期、核验人和可信状态。主档更新不得反向改写历史活动的已确认事实。

## 10. ID、变更与数据一致性

### 10.1 ID 规则

-   使用 UUID/ULID 等稳定内部主键，实施时统一一种。
-   不建立业务展示编号；日常沟通使用项目名称、客户、日期和场地。
-   普通列表默认不显示内部 ID；技术排查或内部链接场景可以查看。
-   API、外键和文件关联必须使用内部 ID，不能依赖名称或日期作为关联键。

### 10.2 操作人与变更

-   单一共享账号、不做角色隔离；每台设备记住上次选择的操作人姓名。
-   重要变更确认、历史恢复、关键文件替换、删除/归档等操作提交前重新确认姓名。姓名是操作记录标识，不等于独立账号认证。
-   普通字段修改直接保存并记录审计。
-   重要变更先创建变更请求；确认前旧值仍是正式值。记录对象/字段、修改前后、来源文件/原文、提出人、确认人、提出/确认/生效时间、版本和结果。
-   任何同事可以确认。提出人与确认人相同时如实记录，不声称双人审核。
-   历史恢复通过新的反向变更实现，不删除旧审计。
-   不同字段的并发更新可以合并；同字段冲突才需人工处理。业务数据、字段版本、关联和审计应事务一致。

### 10.3 唯一事实来源

PostgreSQL 规范化业务记录是正式事实来源。不得以整份 JSONB 状态文档作为正式写入入口再同步投影到业务表，造成双重真值。JSONB 仅可用于原始输入、非结构化附注或只读兼容快照。业务写入通过实体级 API 与事务完成。

## 11. 期限倒推与风险

从场次关键时间向前推导工作包交付节点，再按任务依赖推导定稿、打样、制作、运输和布场期限。只有工期和工作日规则可靠时才给具体建议日期，否则显示"需要确认"。系统建议期限、供应商承诺、实际完成时间分开存储。改期、数量/规格变化或来源文件更新时，将受影响任务标记"需要复核"，不自动完成，也不静默覆盖供应商承诺。任务依赖禁止循环，允许独立任务并行。

## 14. 仍待决定但不阻塞建模的事项

1.  **项目拆分边界**：建议以独立报价、交付责任或验收边界判断；最终由业务人员决定。

4.  **供应商外部编辑**：建议首期只提供受控文件分享，正式业务编辑由内部同事完成。
5.  **归档时机**：建议人工确认项目完结；资料未齐时可标记收尾/待补，不按日期自动归档。
6.  **状态字典管理 UI**：底层支持配置显示名、颜色、图标；完整管理入口是否首期开放，可在交互原型评审时决定。

## 15. 开发门禁

-   **Gate A：业务闭环原型**：需求登记 → 项目 → 场次 → 工作包 → 需求/任务 → 改期预览/确认 → 文件关联 → 验收归档。
